== 1. SQLite schema (Drizzle migrations, raw SQL queries) ==

projects(id TEXT ulid PK, name, path, created_at, archived_at NULL)

sessions(id TEXT ulid PK, project_id FK, harness TEXT /*config key, not FK*/, title, cwd, worktree_path NULL, provider_session_id NULL /*ACP sessionId for session/load*/, kind TEXT 'chat'|'subagent'|'epic_worker', parent_session_id NULL FK /*subagent + fork + btw parent*/, forked_at_seq NULL /*fork point cursor*/, spawned_by_seq NULL /*message that spawned a subagent; direct FK, no projection — kills the t3code-vfi bug class*/, epic_run_id NULL FK, status 'idle'|'running'|'errored'|'archived', auto_resume INTEGER, created_at, last_activity_at)

messages(seq INTEGER PK AUTOINCREMENT /*THE global monotonic cursor*/, session_id FK, turn_id TEXT, item_id TEXT /*groups streamed rows into one logical item*/, role 'user'|'agent'|'system', type 'text_delta'|'thought_delta'|'tool_call'|'tool_update'|'tool_result'|'ask_user_question'|'user_answer'|'attachment_ref'|'turn_start'|'turn_end'|'turn_interrupted'|'error', content TEXT JSON zod-validated, created_at). STRICTLY append-only, no UPDATE ever. Streaming text persists as delta rows flushed every 500 ms or 2 KB; the client folds rows sharing item_id. Replaying rows in seq order reproduces exact UI state, so reconnect is `SELECT * FROM messages WHERE seq > ? AND session_id IN (...) ORDER BY seq`. One global cursor covers every subscription (multi-session views, dashboards). Index (session_id, seq).

attachments(id ulid PK, session_id FK, message_seq NULL, filename, mime, size_bytes, sha256, rel_path, status 'pending'|'complete'|'failed', created_at)

epic_runs(id ulid PK, project_id FK, epic_bead_id TEXT, status 'running'|'paused'|'completed'|'failed'|'cancelled', mode 'pool'|'serial', worker_count, base_branch, config JSON /*subagent+model config*/, started_at, ended_at, error NULL)

epic_iterations(id ulid PK, epic_run_id FK, bead_id, session_id FK /*worker session — this IS the subagent link*/, worktree_path, branch, attempt INTEGER, status 'running'|'merged'|'failed'|'interrupted', failure_reason NULL, started_at, ended_at)

FTS5: contentless-delete virtual tables messages_fts(text extracted from text/tool rows), sessions_fts(title), epic_runs_fts(epic_bead_id, error) kept in sync by triggers on insert.

== 2. packages/protocol (zod, ~1.5k lines) ==
- message.ts: MessageContent discriminated union per `type`; Message = row shape.
- events.ts: ServerEvent = {seq, sessionId, msg: Message} for persisted events, plus Ephemeral union (uploadProgress, sessionStatus, epicRunStatus, presence) with seq: null — ephemera are never replayed, derived state must always be reconstructable from rows.
- commands.ts: HTTP request/response bodies (createProject, createSession, prompt, interrupt, fork, btw, answerQuestion, uploadInit, epicStart/pause/resume/cancel, search).
- ws.ts: single client→server frame {type:'subscribe', sessions:[...]|'all', cursor:number}.
- status.ts: /api/health, /api/status, SSE event shapes for dashboards.
Server, web, and the dashboard client package all import only this package. All types via z.infer.

== 3. Session lifecycle ==
Spawn: insert row → Bun.spawn harness command (stdio pipes; `pty` protocol entries use node-pty) → ACP initialize → session/new(cwd) → store provider_session_id. Prompt: session/prompt; every session/update notification is normalized to Message rows, appended (getting seq), then published on the in-process bus; ws.ts fans out to subscribers. Permission requests are auto-approved (always-yolo). AskUserQuestion surfaces as ask_user_question row; the answer arrives over HTTP, appends user_answer, and resolves the pending ACP request. Idle reap: kill the ACP process after 15 min idle; row stays 'idle'; next prompt respawns.

Resume after server restart (process is gone — resume means resume of the CONVERSATION, not the process): boot recovery pass runs before listen. (a) Every session with status 'running': append turn_interrupted row, set 'idle'. (b) If auto_resume is set (epic workers always; chat sessions that were mid-turn): respawn harness, session/load(provider_session_id) when the agent advertised loadSession, else session/new + one recap prompt built from persisted messages (last user prompt + tool summary); then send "The server restarted mid-turn. Continue." (c) Idle sessions: nothing; lazy respawn on next prompt. Store loadSession capability per harness at first initialize so recovery knows the path without spawning twice.

== 4. Uploads (≤1 GB) ==
POST /api/sessions/:id/uploads → returns attachment id + PUT URL. Client streams the body; server pipes request stream straight to disk at data/projects/<pid>/sessions/<sid>/files/<attachmentId>-<safe-filename>, hashing sha256 en route; progress emitted as ephemeral WS events; on finish, status='complete' and an attachment_ref message row links it in chat as the reference path handed to the agent. Never over WebSocket (t3code had to raise maxPayload to 512 MiB, commit 8e5cf2d02, then moved to HTTP anyway, commit 08f1ac479 — start where they ended). Sweeper deletes 'pending' rows older than 24 h. GET /api/attachments/:id streams with Range support so pdf.js and video work.

== 6. Epic runner (first-party) ==
Reads beads via the `bd` CLI with --json (NOT dolt SQL): bd is the stable interface, works across local/embedded/server topologies, and t3code's BeadsStatusBroadcaster proved the JSON parsing is small and testable; dolt SQL would couple forge to bd's internal schema and the tailnet Dolt server. Watch .beads/last-touched for cheap change signals. Loop: bd ready --parent <epic> → claim → create worktree+branch → create epic_worker session (harness/model from run config) → iterate → merge queue → bd close → next. Worker processes are children of the forge server, owned by runner.ts — never spawned inside an agent turn (t3code memory: headless iterations die at end of turn). Restart recovery: 'running' epic_runs reload; 'running' iterations become 'interrupted', their worktrees reset to branch head, iteration restarts with attempt+1 — fresh-context workers make restart-the-iteration safe and correct. Triage (t3code-7a2 lesson): after 2 failed attempts on one bead, the runner pauses the run, appends a triage card into the run's root session with the failure_reason chain, and waits for a human decision; it never spawns repair children on its own.

== 7. What t3code's event sourcing bought and cost (why the above is right) ==
Bought: audit trail and replay. Cost: ~2.5k lines of decider/projector/normalizer, a 2449-line ws.ts with snapshot fallbacks and replay-gap caps, read models that drift from truth (t3code-vfi), and a 3 GB heap churn to serve 557 events from a stale cursor (ws.ts:1554, t3code-9x8.1). Forge keeps the one thing event sourcing actually delivered (ordered append-only history with a cursor) as a plain table, and drops the rest.

Key files: /home/yiin/Projects/forge/docs/DIRECTION.md; /home/yiin/Projects/t3code/apps/server/src/ws.ts:1543-1560; /home/yiin/Projects/t3code/apps/server/src/provider/acp/AcpSessionRuntime.ts:594-622; /home/yiin/Projects/t3code/apps/server/src/beads/BeadsStatusBroadcaster.ts; beads t3code-9x8, t3code-vfi, t3code-7a2.

### Decisions

- **Message persistence and reconnect**: One strictly append-only messages table with a global AUTOINCREMENT seq as the only cursor; streamed deltas are rows grouped by item_id; reconnect is one indexed SELECT past the cursor plus live tail. — Lossless by construction and ~250 lines of ws code. t3code's event-store replay needed 2449 lines, snapshots, gap caps, and still churned 3 GB heap on a stale cursor (ws.ts:1554, t3code-9x8.1).
- **What resume means after restart**: Resume the conversation, not the process: recovery pass marks running turns interrupted, then respawns via ACP session/load when the agent advertises loadSession, else session/new plus a recap prompt, then an automatic 'continue' prompt for mid-turn sessions and all epic workers; idle sessions respawn lazily. — ACP only guarantees session/load behind the loadSession capability (AcpSessionRuntime.ts:594-622), so a capability-gated load with a recap fallback is the only path that works for every harness.
- **Subagent and epic linkage**: Plain FK columns written at spawn time: sessions.parent_session_id + spawned_by_seq, epic_iterations.session_id. No derived read models. — t3code derived subagent cards from projections and shipped 'No subagent details are available' (t3code-vfi). A FK written in the same transaction as the spawn cannot drift.
- **Epic runner beads access**: bd CLI with --json flags plus an fs.watch on .beads/last-touched; no direct dolt SQL. — bd is the stable public interface across beads topologies; t3code's BeadsStatusBroadcaster proved the JSON parsing is small and testable. Dolt SQL couples forge to bd internals and the tailnet server.
- **Epic run restart semantics**: Running iterations become 'interrupted', worktrees reset to branch head, iteration restarts fresh with attempt+1; after 2 failed attempts on one bead the run pauses and surfaces a triage card instead of retrying. — Fresh-context workers make restart-the-iteration safe. t3code-7a2 shows unbounded retry/repair spawning hides root causes; pausing with the failure chain gives the human a real decision.
- **Uploads**: HTTP streaming PUT to disk beside the session (data/projects/<pid>/sessions/<sid>/files/), sha256 while streaming, ephemeral WS progress events, attachment_ref message row carries the reference path; Range-capable GET for viewers. Never over WebSocket. — t3code first raised WS maxPayload to 512 MiB (8e5cf2d02) then moved uploads to HTTP anyway (08f1ac479). Start at the destination; streaming to disk handles 1 GB without buffering.
- **Ephemeral vs persisted events**: Protocol splits ServerEvent (has seq, persisted, replayable) from Ephemeral (seq null, never replayed: progress, presence, live status); all durable UI state must reconstruct from rows alone. — This one rule is what makes cursor replay complete — if a UI state needed an ephemeral event, reconnect would silently lose it.
- **Server shape and budget**: Flat module map, ~19 files, ~6k server lines (map with per-file budgets in findings); protocol ~1.5k; leaves 20-40k for the web app within the 30-50k target. — Budgets per module keep the t3code growth pattern (9.3k lines in orchestration alone) from recurring; every module has one owner responsibility.

### Risks

- Bun compile spike: bun build --compile with node-pty is unproven here; DIRECTION already names the Node 24 fallback — run the spike as the first child so the schema/module plan does not sit on an unverified runtime.
- loadSession support varies by harness build; the recap-prompt fallback loses in-context tool state, so a resumed session on a non-loadSession agent continues with summary context only. Acceptable, but the UI should mark such turns 'resumed with recap'.
- Global AUTOINCREMENT cursor assumes exactly one writer process per machine; if forge ever shards or clusters, the cursor scheme must change. Fine for one-instance-per-tailnet-machine.
- Delta rows inflate the messages table on very chatty tool output; the 500 ms / 2 KB flush bounds it, but FTS triggers should index only finalized text rows or search cost grows with delta noise.
- 1 GB streaming through Hono on Bun needs a backpressure check (req.body pipe to Bun.file writer) in the test harness before the upload UI lands.
- pty-protocol harnesses have no turn boundary from the protocol; quiet-period detection is heuristic and will sometimes split or merge turns.

## Prior art: t3code lessons, /btw+forks design, ACP ecosystem

## 1. t3code defects forge must design out

RECONNECTION. t3code streams events over stateful WS subscriptions. Every reconnect path was a bespoke patch: clear tracked RPCs (commit f5ecca448), preserve live stream subscriptions (94d13a2b7), ignore stale lifecycle events from the old socket (dbebc387d), harden recovery (528bb2a1f), skip healthy env reconnects after browser resume (90eea047a). Root cause: push-only streaming with no durable cursor, so client state and server state drift on every drop. Forge's DIRECTION cursor-replay design (`messages where id > last_seen`) removes the whole class. Keep the WS dumb (a "new data" ping), make HTTP commands idempotent, and replay from SQLite.

SERVER RESTART. A restart killed harness processes mid-turn and threads sat stopped silently until a human typed (commit 6f372ce14 added a boot pass that resumes and nudges; e6a217aaa fixed its race). Two hard lessons inside that commit: (a) Codex and OpenCode silently open a BLANK session on a stale resume cursor, so a resume must be proven by a durable settled event before you tell the agent to continue; (b) graceful SIGTERM and SIGKILL leave different state shapes, so the boot pass must read the projection BEFORE any reconciliation. Forge's auto-resume scope must build this boot sweep on day one: collect interrupted turns first, settle them as interrupted, resume with proof, nudge once, exclude epic iterations and children.

SUBAGENT UX. Four full epics (t3code-09a inline cards, t3code-66x inspector/transcript/steer-stop, t3code-vzb roster+drawer+thread-backed spawn, t3code-8qw orphan cleanup) plus still-open bugs: t3code-vfi (card shows "No subagent details"), t3code-jpy (live spawn auto-cancelled mid-run), t3code-bll (two competing read models). Root causes, per commit ce2ab6bbe and bead t3code-dpq: (a) provider events carry no shared correlation id — an opencode spawn lands as three activities with no common key, forcing title-match heuristics; (b) TWO read models (activity-derived groups vs thread.subagents) that disagree; (c) in-memory SpawnRegistry dies on restart, producing phantom "running" rows with ticking timers; (d) the spawn tool blocks the parent turn and dies with it. Forge design-out: one durable subagents table keyed by a stable id stamped at ingestion, one read model, non-blocking child lifecycle (the t3code-jx0.12 design), and honest "unknown" rendering when the harness gives no signal. Note: over ACP the subagent signal is a heuristic (t3code-6qj), so design the UI to degrade gracefully.

EPIC RUNNER UX. t3code-7a2 (P0, open) is the big one: the runner has no failure triage. Run 87a9d295 burned 19 iterations on a broken node_modules because the runner cannot classify infra vs code failure. Missing capabilities it names: control-run classification (reproduce the gate on the unmerged base), failure-signature memory and loop detection, capped merge-fix depth with actual gate output handed to the repair child, set-level (not branch-vs-base) reconciliation, environment preflight, self-heal for dependency installs, and a terminal "needs operator" state with a diagnosis. Smaller UX debts: sidebar showed raw bead ids as titles (t3code-76n, t3code-zy0 — this drove forge's intelligent-title requirement), CLI-launched runs cannot nest under their thread because originThreadId is hardcoded null (t3code-w2l), stranded branches from a dead run need manual adoption (t3code-dqs), run "done" once ignored the merge queue (t3code-xig).

## 2. The /btw and chat-forks epic to copy: t3code-jx0

Epic t3code-jx0 "Add conversation branches, edit forks, and side chats" (planned 2026-08-17, all 16 children open — t3code never built it, forge gets it first). Full design:

Vocabulary (use exactly): conversation family, path, side chat, managed agent, source boundary, context method, context confidence. "branch" means a Git branch only. Ancestry uses separate family and parent fields — never reuse parentThreadId (that means agent-owned subagent). A user edit forks BEFORE the source user message; an assistant branch INCLUDES the selected settled assistant message. Active path selection, drafts, focus, scroll stay client-local.

Decisions recorded on the epic: shared checkout is the default for child work; side chats disappear on close unless kept as paths; many side chats share one searchable tray; persistent paths use inline sibling arrows plus one collapsed sidebar family slot; the original path can keep running during an edit fork. Do-nots: never label turn/tail/synthetic context as an exact fork; never claim a transcript fork restores historical workspace files; never block the parent when a child starts; never store discardable side chats in the permanent log.

Children (the build plan): jx0.2 durable family contracts (familyId, parent, relation kind, source boundary, context method+confidence, workspace mode, retention state; existing threads load as one-member root families with own id as family id). jx0.1 provider fork capability contract + conformance suite (distinguish exact-message / completed-turn / session-head / synthetic-replay / fresh-context; runtime capability can reduce a static claim; never a silent fresh session). jx0.4 native fork paths (Codex thread/fork at completed turn; Claude resume at historical user UUID; ACP session/fork only when advertised). jx0.5 explicit transcript-replay fallback (serialize roles through the boundary, copy readable attachments, record synthetic context with reduced confidence, token-limit warnings). jx0.6 one idempotent atomic fork command (pending child relation → resolve context → copy attachments to child-owned ids → send edited text; boot sweep resumes pending forks). jx0.8 inline Edit + "Branch from here" actions (Escape cancels, failed fork keeps text, streaming assistant shows disabled reason). jx0.9 sidebar family navigation (sibling arrows with position/total, one collapsed family node). jx0.10 side-chat lifecycle (frozen source boundary, outside permanent tree, atomic Keep-as-path promotion, crash expiry, discard stops the provider session). jx0.11 the /btw tray itself: singleton tray, many temporary tabs, /btw or a header action creates+sends once while the parent route stays active; shows source message, context method, tools, workspace mode, status, Keep as path, Discard; only the selected child stays subscribed; tablist with roving focus; full-screen child surface on phones. jx0.12 non-blocking managed child agents (durable lifecycle outside the in-memory registry, depth/concurrency limits). jx0.13 shared-checkout file-overlap warnings (turn diffs, name the sessions, no auto-merge). jx0.7 tree-aware close/archive/delete.

## 4. ACP ecosystem (verified on npm today)

Protocol lib: @zed-industries/agent-client-protocol 0.4.5 (official TS; Rust crate exists). Adapters: Claude Code — @zed-industries/claude-code-acp 0.16.2 (official, over the Claude Agent SDK) and community acp-claude-code 0.8.0. Codex — @zed-industries/codex-acp 0.16.0 (Rust binary, npm-wrapped). Kimi — native `kimi acp` (t3code KimiAcpSupport.ts:35-36). Cursor — native `cursor-agent ... acp` (CursorAcpSupport.ts:39-42). Grok — `grok agent stdio` (GrokAcpSupport.ts:38-39). Gemini CLI — native `--experimental-acp`. OpenCode — community opencode-acp 1.14.25 (t3code drives opencode through its own server API instead). acp-factory 0.1.15 is a community spawn-and-manage lib. t3code's packages/effect-acp generates its schema from the ACP spec and already exercises the full surface.

Capabilities forge relies on: baseline session/new, session/prompt, session/cancel, session/update (all agents MUST support). session/load is a top-level loadSession capability (schema.gen.ts:2019) — the lossless-resume path. UNSTABLE: session/resume (resume without history replay, schema.gen.ts:4916) and session/fork (schema.gen.ts:539) — both must be capability-gated per agent. Client-side services forge must implement: fs/read_text_file, fs/write_text_file, terminal/* (the client hosts terminals), session/request_permission (forge is always-yolo: auto-approve everything server-side), available_commands_update (slash-command lists; t3code-vst.19 used it for Kimi). promptCapabilities govern attachments; t3code had to encode non-image attachments specially for the ACP trio (t3code-vzb.38) — forge's upload-as-reference-path design sidesteps this.

Known adapter defects from t3code probes: kimi-code emits no session/update for autonomously-started turns (subscription created per-prompt; reported upstream as MoonshotAI/kimi-code#3177, bead t3code-s5u.7); Kimi/Grok/Cursor treat a mid-turn prompt as a new turn, not a steer (epic t3code-6f3 probed this on the wire); ACP has no first-class subagent signal, t3code-6qj detects them heuristically.

### Decisions

- **Reconnection**: Copy nothing from t3code's WS recovery code; rely on DIRECTION's cursor replay plus idempotent HTTP commands and a dumb notify-only WS — Five separate t3code commits patched one root cause: stateful push streams with no durable cursor
- **Restart resume**: Copy t3code's boot-pass design (commit 6f372ce14): read projection before reconciliation, settle interrupted turns, resume with durable proof, nudge once — Provider resume is untrustworthy; ACP agents can open a blank session on a stale cursor, and only a settled resume event separates 'carry on' from amnesia
- **Subagents**: One durable subagents table with a stable id stamped at ingestion, one read model, non-blocking child lifecycle; avoid in-memory registries and title-match heuristics — t3code spent four epics and still has open bugs (vfi, jpy, bll) because correlation was heuristic and lifecycle state lived in memory
- **/btw and forks**: Copy epic t3code-jx0 wholesale: vocabulary, decisions, do-nots, and the child breakdown; collapse the provider fork matrix to ACP session/fork-when-advertised else synthetic replay with honest context-confidence labels — The design is complete and never built; forge's ACP-only stance removes most of its provider complexity
- **Epic role policy**: Copy the EpicRolePolicy shape (roles→tiers→hops with utilization skip, account rotation, six default in-session stage subagents shipped tier-less) as plain zod — It is proven, and its two documented traps (machine-local instance ids in shipped tiers, silent tool narrowing) are already solved in the comments
- **Runner triage**: Build t3code-7a2's missing capabilities into forge's runner from the start: control-run classification, failure-signature memory, capped repair depth with real gate output, terminal needs-operator state — The worst t3code runner failure (19 wasted iterations) came from retry-only vocabulary, not from any single bug
- **Runner scope**: Copy the cheap high-value runner mechanics (effects-based done proof, run lock with dead-holder reclaim, execution.mode auto, conflict radar, merge-fix context packets); defer the batched-gate bisection machinery until parallel runs demand it — The merge-queue/gate half generated 30+ infra bugs in t3code and threatens the 30k-50k line budget
- **Test harness**: Build test-forge-app on the test-t3-app pattern (isolated home dir, printed ports, guarded sqlite seeding) plus a fake ACP agent modeled on apps/server/scripts/acp-mock-agent.ts with an unsolicited-update mode — The pattern is proven, and tailnet-only auth lets forge drop the pairing-token half
- **ACP adapters**: Ship default harness configs for claude-code-acp, codex-acp, kimi acp, gemini --experimental-acp; treat cursor/grok/opencode as user-addable entries; gate session/load, session/resume, session/fork per advertised capability — Adapters exist for every target harness, but capability and quality vary, so the config-entry model plus capability gating absorbs the variance
- **Titles and run nesting**: Generate plain-word session titles server-side and carry originThreadId through every launch path including CLI — t3code shipped raw bead ids as titles (76n, zy0) and hardcoded originThreadId null in the CLI (w2l); both are one-line-of-design fixes when done early

### Risks

- ACP session/fork and session/resume are UNSTABLE spec extensions; an adapter update can drop them, so the jx0-style fork feature must always keep the synthetic-replay fallback working.
- Kimi's ACP server drops session/update for autonomous turns (MoonshotAI/kimi-code#3177, open as of 2026-08-23); forge sessions on Kimi will look frozen during background-triggered turns unless the UI states this.
- Kimi, Grok, and Cursor cannot absorb a mid-turn steer over ACP (a prompt starts a new turn); the conflict radar and /btw-adjacent steering features degrade on those harnesses.
- ACP has no first-class subagent signal; forge's subagent roster will be heuristic for ACP-native harnesses exactly where t3code still has open bugs, so the UI must render honest unknowns.
- The t3code-jx0 epic is a design, not a shipped feature; no part of it is field-tested, including the atomic fork command and Keep-as-path promotion.
- Copying even the trimmed runner mechanics (lock, merge queue, radar, triage) is the single biggest threat to the 30k-50k line budget; t3code's equivalent surface consumed multiple epics of infra fixes.
- npm version checks reflect today (2026-08-25); adapter maintenance varies (opencode-acp and acp-claude-code are community-run) and should be re-verified at build time.
